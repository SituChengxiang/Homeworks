> 工具：Qoder（桌面端 Agentic 编程助手）

## 第 1 轮：提出题目，询问拆解方式

**我问：** 把完整题目贴给模型——核固定 (0,0)、电量 97e，α 粒子质量 4、电量 2e，
约化单位（e / 相对分子质量 / A / k=1），算六条轨迹并画图，
要求分模块写代码、记录交互过程、坐标限制 ±22.5、颜色或虚实区分、每条曲线有文字标识。
然后问："我该怎么一段一段给你发 prompt 呢？"

**模型答：** 不需要分段发，题目已经完整。给出两条路线让我选：
一是让模型一次做完、把对话本身作为交互记录；
二是按"物理建模 → 数值方法 → 代码实现 → 画图"分步问，交互记录更像逐步讨论。
我选了第二条的思路，但让模型先把环境和技术路线确认清楚。

## 第 2 轮：C89 开发环境

**我问：** 开发环境要求 C89，装了 CLion，但 Linux 上是不是没有 C89 的环境？

**模型答：**（实际动手验证，而不是凭印象回答）
- 机器上 `gcc 16.2.1`，`gcc -std=c89 -pedantic-errors` 可正常编译；
  并用一个含 `math.h`、`printf` 的最小程序实测跑通。
- CLion 走 CMake，需要 `-std=c89 -pedantic-errors` 严格锁定。
- **真正的限制只有一个：C89 标准库没有绘图能力。** 而且 `popen` 调 gnuplot 属于
  POSIX 扩展，在 `-pedantic-errors` 下会直接编译失败。

这一轮把整个项目唯一的技术瓶颈定位出来了：画图环节必须想办法绕出 C89。

### 补充：第 8 轮才发现的 CMake 坑（值得记进报告）

最后做"从零可复现"验证时，按直觉写的 `set(CMAKE_C_STANDARD 89)` 让 CMake **直接 configure 失败**：

```
Target "alpha_scattering" requires the language dialect "C89".
But the current compiler "GNU" does not support this, or CMake does not know the flags to enable it.
```

而 `gcc -std=c89` 明明可用。定位结论：这是 CMake 4.4 的**编译器特性表不认识 GCC 16
这个新版本号**造成的误报，不是编译器的问题。
**改法：** 绕开特性表，显式 `add_compile_options(-std=c89 -pedantic-errors ...)`，
再用 `check_c_compiler_flag("-std=c89")` 探测一次兜底。

顺手做了个**反向测试**证明 C89 是真的被锁死、而不是"没报错而已"：
拿一段带 `//` 注释和 `for (int i = 0; ...)` 的 C99 代码去编，
gcc 明确报出两条 `error:` 并拒绝编译。

## 第 3 轮：确定技术路线

**模型给选项：**

| 议题 | 备选 |
|---|---|
| 画图 | ① C89 用 `fprintf` 直接生成 SVG ② C89 只算数据，Python/gnuplot 画图 ③ 两个都做 |
| 数值方法 | ① 四阶 Runge-Kutta ② Verlet 辛积分 ③ 欧拉法 |

理由：模块划分最干净（计算与绘图彻底分离），符合老师"分模块"的要求。

## 第 4 轮：物理建模，约化单位到底怎么用

**模型先做量纲核对，再写代码。** 用约化单位下的 k=1 得

```
F = k q₁ q₂ / r² = 97×2 / r² = 194 / r²      （斥力，沿径向向外）
a = F/m = 194/(4 r²) = 48.5 / r²
```

化成一阶系统（RK4 要求的形式），状态向量 `{x, y, vₓ, v_y}`：

```
dx/dt = vₓ ,  dy/dt = v_y
dvₓ/dt = 48.5 · x / (x²+y²)^1.5
dv_y/dt = 48.5 · y / (x²+y²)^1.5
```

**模型主动指出两个我原本没想到的物理陷阱：**

1. **几何撞击参数 b = |y₀| = 20 不能直接代进卢瑟福公式。**
   粒子起始位径 √(20²+20²) = 28.28，已经处在相互作用区**内部**，
   真正的渐近撞击参数是 `b = L/(m·v_∞)`，算出来是 9.50 / 12.59 / 17.02。
2. **上下两组轨迹关于 x 轴严格镜像**（初速度沿 x，初始位置只差 y 的符号）。
   这等于送了一个免费正确性检验：程序里 case 1 与 case 4 的 E、|L|、r_min 必须完全相同。

另外确认：六条轨迹的总能量 E = 8.86 / 11.36 / 24.86 全部为正，
且势能是斥力正势，所以六条都是**散射双曲线**，不存在被俘获的椭圆轨道。

## 第 5 轮：分模块实现

**模型给出的模块划分**（也是最终代码结构）：

```
cases.h/.c        六组初值与文字标签        ← 题目数据集中一处
units.h           约化单位常量、绘图框、奇点保护
coulomb.h/.c      加速度 / 势能 / 位径       ← 只有物理
rk4.h/.c          通用四阶 RK 单步           ← 只有数学，通过函数指针接收右端项
trajectory.h/.c   推进 + 终止判据 + 采样 + 守恒量诊断
rutherford.h/.c   解析解，给数值结果当标准答案
export.h/.c       写 .dat 与汇总表
main.c            调度
plot.py           作图
```

**解耦的关键设计：** `rk4.c` 不知道这是库仑力，`coulomb.c` 不知道什么是步长。
换积分器只动 `rk4.c`，换力律只动 `coulomb.c`。

模型在实现过程中自己修正的一个问题：`Trajectory` 最初用静态大数组，
200000 点 × 5 个 double ≈ 8 MB，放在栈上会溢出（C89 没有变长数组），
改成 `malloc` 堆分配 + 容量溢出保护。

## 第 6 轮：运行、校验，发现两个真 bug

第一次编译：`-std=c89 -pedantic-errors -Wall -Wextra` 零警告通过。
第一次运行的结果里，模型抓到两个问题——**这两个都是真错，不是风格问题**：

**bug 1：`r_min` 不适合当收敛性探针。**
最初用 h、h/2、h/4 三个步长比较"最近距离 r_min"来验证 RK4 四阶收敛，
结果 case 1 算出"实测阶数 21.72"这种荒谬值。
原因：r_min 是**离散步点上取 min**，不是光滑泛函，误差不按 h⁴ 走。
**改法：** 在 `RunControl` 里加 `stop_time` 模式，让三个步长各自积分到
**同一时刻** t = 8，比较该时刻的轨道坐标 —— 这才是可比的、光滑的检验量。
改完实测阶数 4.02 ~ 4.07，与理论四阶吻合。

**bug 2：`.dat` 文件头的解析对照值全是 0。**
`main.c` 里的顺序是"积分 → 写文件 → 算解析量"，
所以文件头注释写入 `r_min_exact` 和卢瑟福偏转角时它们还是 0，
而终端表格是在之后打印的，所以看起来是对的——**典型的"终端对、文件错"**。
**改法：** 把解析量计算移到写文件之前。

修完的表头：
```
# r_min     : numeric 25.44745097   analytic 25.44745092
# theta     : in-frame 58.9407 deg   Rutherford asymptotic 98.0913 deg
```

**最终三重验证：**
1. 守恒量：六条轨迹全程 `max|ΔE|/E`、`max|ΔL|/L` 均 < 1e-14（双精度舍入水平）。
2. 解析对照：r_min 数值 vs 卢瑟福解析值，吻合到 1e-7 以上。
3. 收敛阶：h / h/2 / h/4 误差比稳定 ≈ 16，实测阶数 ≈ 4。
4. 镜像对称：case 1 与 case 4 的 E、|L|、r_min 完全一致。

## 第 7 轮：画图，两次迭代

**第一版：文字标签全部消失。**
标签按"沿曲线法向朝远离原点方向外推"摆放，但曲线本来就贴着 y = ±22.5 边界跑，
外推直接推出框外被裁掉了。另外那个 r₀ 参考圆在 ±22.5 的框里只剩两条斜线段，
看起来像杂散线，很误导 —— 删掉。

**第二版：标签互相重叠。**
改成朝原点一侧（图中央大片空白区）摆放后标签出现了，但三条上组标签挤在一起，
左下角的方法说明文字压在曲线上。

**最终版：** 引导线起点由弧长参数自动算（`arc_point`），
文字位置按六条曲线的实际几何手工错开（`LABEL_LAYOUT`），
方法/单位说明移到 figure 页脚，不再与数据区争位置。
图例用"颜色 = 初速度三档，实线/虚线 = 初始位置在上方/下方"双编码，
并补一条 `未偏转入射方向` 的虚线参考，让偏转幅度一眼可比。

## 附：可复用的 prompt 模板

这轮交互里真正起作用的是下面几句，换个题目也能照抄：

1. **交代约束而不是解法**
   "环境要求 C89，用 CLion；题目要求分模块写代码。"
   —— 把硬约束说清楚，模型会自己去验证环境、自己发现"C89 不能画图"这个瓶颈。

2. **要求先核对物理再写代码**
   "先别写代码，约化单位下加速度系数是多少？这六条轨迹能量是正还是负？"
   —— 正是这一问把 b ≠ 20、六条都是散射双曲线这两个坑提前挖出来了。

3. **要求给出独立验证手段**
   "数值解怎么证明是对的？"
   —— 模型给了守恒量 + 解析解对照 + 步长减半收敛三重验证。
   收敛性检验那一步就是它自己发现探针选错、又改对的。

4. **对图提具体要求并检查**
   "标签别挡住曲线，每条曲线都要能一眼对上文字。"
   —— 第一版和第二版的图都有问题，必须让模型把图渲染出来看，不能只写完就交。
